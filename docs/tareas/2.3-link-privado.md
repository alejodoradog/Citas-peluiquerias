# 2.3 Link privado del barbero
Estado: construida el 2026-11-10, pendiente del CI (pgTAP y de punta a punta no corrieron en local: Docker estaba apagado). Tiene la aprobación general del fundador al plan. Las decisiones de abajo quedan provisionales hasta que el fundador las confirme.
Objetivo: el dueño genera, copia, comparte, reemplaza y desactiva el link privado de cada barbero (D-56), y ve su estado en D-53 y D-54. El link solo existe en la respuesta al toque del dueño: la base de datos guarda su SHA-256.
Diseño: `docs/diseno/D56-Link-barbero.dc.html`, copiado de Claude Design el 2026-11-09.

## Decisiones provisionales (2026-11-10)
1. **Un toque, un link.** Cada "Copiar link nuevo" o "Crear link nuevo" emite un token nuevo y el anterior deja de servir en la misma sentencia. En la misma visita, "Copiar otra vez" y "Compartir" reusan ese link sin emitir otro. Al salir de la pantalla o recargar, el link se pierde: nunca va en el HTML del servidor.
2. **Confirmación** (hoja inferior) antes de reemplazar un link enviado y activo ("Kevin deja de entrar con el que tiene") y antes de "Desactivar link". El primer link (sin enviar) y "Crear link nuevo" (desactivado) no la piden: no hay un link que funcione para dañar.
3. **Sin botón "Enviar a …" hasta la tarea 5.2** (correo con SES). "Compartir" (menú del sistema) cubre WhatsApp y el correo del celular. Sin `wa.me` (`docs/decisiones/0006-correo-unico-canal.md`).
4. **Un barbero inactivo puede recibir un link nuevo:** con él atiende las citas que ya tenía (spec). D-56 lo avisa.
5. **`barbers.link_issued_at`** guarda cuándo se emitió el link que funciona, para "link sin enviar" (D-53, en minúscula tras el separador, como el diseño), "Aún no se lo has enviado" y "Enviado el 3 de noviembre" (D-54 y D-56). Lo escribe solo un trigger; las sesiones lo leen.
6. **(4.4) Link desactivado, reemplazado o inexistente:** la vista del barbero muestra el mismo mensaje genérico en los tres casos. Solo se anota aquí.
7. **(5.5) Con la suscripción suspendida** el dueño puede desactivar y reemplazar links (es seguridad, no uso). Solo se anota aquí.

No hay botón "Activar": un link desactivado solo vuelve con un token nuevo, y el trigger lo impone.

## Decisiones provisionales de textos (para el fundador)
1. El aviso de D-56 dice **"Cada link nuevo reemplaza al anterior"** en vez de "Cada vez que copias o envías el link, se crea uno nuevo" del diseño: "Copiar otra vez" y "Compartir" no crean otro (decisión 1).
2. **"Copiar link nuevo"** es el botón principal (el diseño ponía primero "Enviar a …", que llega con la 5.2).
3. **"Desactivar link" no aparece mientras el link nunca se ha enviado:** nadie lo tiene, no hay nada que cortar.
4. Tarjeta **"Este link solo se muestra ahora"**, con "Envíaselo a Kevin ya. Si sales de esta pantalla, tendrás que crear otro.", el link seleccionable, "Copiar otra vez" y "Compartir".
5. Texto para compartir: "Hola, Kevin. Con este link ves tu agenda en Yapoin. No se lo pases a nadie." (título "Tu agenda en Yapoin").
6. Confirmaciones: "¿Crear un link nuevo?" / "Kevin deja de entrar con el que tiene. Tendrás que enviarle el nuevo." y "¿Desactivar el link de Kevin?" / "Kevin deja de entrar a su agenda al instante. Para que vuelva a entrar tendrás que crearle un link nuevo."
7. Con el barbero inactivo, el alcance dice "ve su agenda del día y la semana y marca las citas que ya tenía", sin "y bloquea sus horas" (spec: un barbero inactivo no recibe bloqueos nuevos). Ver la pregunta b.

## Preguntas para el fundador
- **a.** La ayuda de "Desactivar link" (del diseño) dice "Úsalo si Kevin perdió el celular o se fue". La spec (línea 33) dice que si el barbero se va se **desactiva al barbero**, y con su link sigue atendiendo lo que tenía. ¿Quitamos "o se fue", o se quiere que también se corte el link en ese caso?
- **b.** ¿Está bien el alcance sin "bloquea sus horas" para un barbero inactivo (ya aplicado, trivial de revertir)?
- **c.** "Enviado el …" se sella cuando el dueño **copia o comparte** un link nuevo, no cuando el barbero lo recibe (la app no puede saberlo). ¿Sirve así, o el texto debería decir "Creado el …"?
- **d.** Un link por visita: si el dueño sale de la pantalla y vuelve, ya no lo ve y debe crear otro (que corta el anterior). ¿Aceptable?

## Base de datos
- `20261110060000_add_barber_link_rules`:
  - `barbers.link_issued_at` (`timestamptz`), con `grant select` a `authenticated`, sin insert ni update; `anon` no la lee;
  - trigger `guard_barber_link` (security invoker, `search_path` vacío): en insert la deja nula; en update la sella con `now()` solo si el link queda activo con un hash nuevo, y rechaza (23514, `link_needs_new_token`) encender un link apagado con el mismo hash;
  - check `barbers_owner_has_no_link`: el barbero del dueño nunca tiene link activo (antes, un `update` apaga el link de cualquier dueño que lo tuviera).
- La app escribe con un `update` por columnas filtrado por barbería, id y `is_owner = false`; nada lee `link_token_hash` (las sesiones no pueden).

## Contrato para la 4.4 (vista del barbero)
- `public.barber_agenda_access(p_token text)`, `security definer` con `search_path` vacío, `grant execute` a `anon`.
- Valida el formato `^[A-Za-z0-9_-]{16,128}$` antes de hashear; busca `encode(sha256(convert_to(p_token, 'UTF8')), 'hex') = link_token_hash and link_active`.
- Sin filas en cualquier falla (formato, desactivado, reemplazado, inexistente): mismo mensaje genérico (decisión 6).
- Acepta barberos inactivos (decisión 4). Nunca devuelve el hash.
- Cada acción posterior (marcar cita, bloquear horas) vuelve a validar el token en la misma función, no confía en una sesión.
- Encabezados en `/b/:path*` (ya en `next.config.ts`, con prueba unitaria y de punta a punta): `Referrer-Policy: no-referrer`, `Cache-Control: private, no-store`, `X-Robots-Tag: noindex`. Next.js puede reemplazar `Cache-Control` en páginas dinámicas por el suyo (`private, no-cache, no-store, …`), que también impide guardarla; la 4.4 lo verifica en la URL desplegada. OG genérico (sin nombre del barbero). El GET nunca muta; la RPC va por POST. Los registros de peticiones de Vercel guardan la ruta, token incluido: la 4.4 decide si el token va en el fragmento (`#`) o se cambia por una cookie al primer ingreso.

## Riesgos conocidos
- **Dos pestañas o dos toques casi simultáneos:** el último `update` gana y el link que mostró la otra pestaña ya no sirve. Es lo que promete la pantalla ("cada link nuevo reemplaza al anterior"); el botón se deshabilita mientras espera.
- **Desactivar y emitir a la vez** (dos pestañas): queda lo último que llegó a la base; la pantalla se refresca con el estado real.
- **Una sesión del dueño puede escribir `link_token_hash` a mano** (PATCH directo a PostgREST): elegir su propio token o volver a poner el hash de uno retirado que conserve (la base no guarda hashes retirados). Se **acepta como riesgo bajo**: la sesión del dueño ya emite links válidos cuando quiere, y la decisión 0002 permite que la sesión escriba el hash. Arreglo propuesto, **pendiente de decidir antes del piloto**: una RPC `issue_barber_link(p_barber_id)` security definer (search_path vacío, verifica membresía y `is_owner = false`) que genere el token en la base con `gen_random_bytes(32)`, guarde su hash y lo devuelva una sola vez, y quitar a `authenticated` los grants de update/insert sobre `link_token_hash` y `link_active` (con otra RPC para desactivar).
- **Copiar en el iPhone:** se entrega al portapapeles una promesa del link en el mismo toque (`ClipboardItem`); si falla, se escribe al llegar y, como último recurso, el link queda visible y seleccionable. El portapapeles solo se prueba en Android.
